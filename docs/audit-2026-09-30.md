## Fix first: behavior and data trust

1. **Search has contradictory results — confirmed in browser.** `apps/web/src/Overview.jsx:129–143,342–370` excludes the first two categories from `matching` and renders them unconditionally. Searching `arrays` leaves Arrays and Dynamic programming visible while saying “No matching patterns.” Filter all categories first; feature only eligible results; calculate empty state from the complete result set.

2. **Attempt editing/removal is unreachable — confirmed source and browser.** `apps/web/src/AttemptEditor.jsx:5` has no caller. `PatternProblems.jsx:130–143` only displays history date and assistance. Restore per-attempt actions for editable recordings, preserving revision conflict handling and deletion confirmation. Also expose notes and the recorded approach; distinguish editable recordings from provider imports.

3. **History is permanently truncated — confirmed source.** `PatternProblems.jsx:82,143` requests six entries at offset zero and shows “More earlier records exist” without a way to load them. Add load-more pagination and an explicit retry control. Cache invalidation must include changes/version: the current history is fetched once and can stay stale through dashboard refreshes.

4. **Account isolation covers imports but not recording — confirmed source gap.** `repository.js:38–41,94,125` verifies import accounts. `capture()` at line 156 and the recording payload contain no username/account check. Switching the signed-in LeetCode account can therefore record into the same workspace. Decide whether a workspace is strictly tied to an account; if so, enforce it for captures, not just imports. No account switching was performed during review.

5. **Legacy-to-dated score transition can decrease strength — reproduced with a pure function.** `retention-policy.js:69–74` normalizes undated experience by persistent weights (0.8), then switches to the dated formula after the first dated event. For 100 distinct problems, breadth target 20, no revisits: legacy-only 58.97; adding one current imported solve with unknown assistance gives 52.88. Even an independent solve gives 58.58. Trend can display this measurement transition as a negative practice trend. Choose a continuous baseline or clearly distinguish estimated experience and dated strength. This is a policy decision with a measurable, surprising consequence.

6. **Missing difficulty does not recover on reimport — confirmed source.** `repository.js:104,134,166` uses insert-on-conflict-do-nothing. A problem initially captured with null difficulty keeps null even when imports later provide it; unknown difficulty gets no goal credit. Fill missing provider metadata without overwriting intentional user edits, and surface unresolved metadata with a repair path.

7. **Background failure removes the dashboard — confirmed source.** `Overview.jsx:84–108` replaces the data result with an error on a failed 60-second poll. Keep the last successful view with a stale/offline notice, timestamp and retry. Reserve the full error screen for initial-load failure.

8. **New captures can be swallowed by an existing panel — confirmed source behavior.** `capture.js:12` returns immediately if the same problem already has a panel. A second fresh Accepted while the previous prompt is open does not create another recording opportunity. Represent pending submissions separately or explain which submission is being recorded and provide a queue/action.

9. **Unsubmitted choices disappear — confirmed source.** `capture.js:9,24,58` only persists a payload after Save. Close, navigation or refresh loses a selected-but-unsaved form. Persist an editable draft separately from the immutable uncertain-save payload. Frozen retries are valuable and should remain immutable until reconciliation.

10. **Conflicted frozen recordings lack reconciliation — source-derived edge case.** `service-worker.js:15–16,29–33` retains payloads for 409 responses. The API can return 409 for a reused/deleted recording ID; the panel remains locked and only offers retry. Safely distinguish a committed save, recoverable network uncertainty and a definitive conflict. Offer a concrete recovery path after checking server state; do not simply change request IDs after uncertain saves.

## Website usability and product clarity

11. **Navigation has no URL/history state.** `Overview.jsx:71–72,165–166` stores selection only in React. Reload loses category/subpattern; Back does not traverse app views; details cannot be bookmarked. Add URL state for category, subpattern and optionally problem search/page. Restore focus and scroll when returning to the dashboard.

12. **Global search stays visible in details but has no visible effect there.** The detail branch ignores `query`. Either search navigable patterns with results while viewing details, or adapt the header field to its active context.

13. **Goal credit needs a breakdown.** In the live Arrays view, 96 distinct solves produced 23/75 credited coverage, with Easy 63/16 and Medium 32/47. Credit is capped per subpattern and difficulty, then summed; even category-level surplus can coexist with missing subpattern quotas. Explain credited solves versus total solves and show exactly where remaining quotas are. The current sidebar explanation mentions difficulty but not subpattern caps.

14. **Explain ordering and featured rows.** The first two rows are highlighted without a reason label. Goal ordering uses a weighted attention score (`goal-policy.js`) combining deficit and practice weakness, while the subpattern copy says gaps first and weakness only breaks ties. Align copy with the actual ranking and expose the reason for a highlight. Consider explicit goal-gap and practice-strength sorting if both are useful.

15. **Mobile header overflows — confirmed.** At a 375px viewport, document/header scroll width was 380px. `App.jsx:36,95–105` fits brand, fixed-width search and Refresh on one row. Use a compact refresh icon or second-row search. Check 320px, 375px, 768px, 1024px, 1440px and 200% zoom before closing responsive work. `PatternCard.jsx:45,71` fixed minimum columns also deserve tablet testing.

16. **Goal summary takes too much space on smaller desktop/tablet.** Below xl, `Overview.jsx` puts goal content before the working view. The live default-width screenshot had a large goal block before the first pattern. Consider a compact summary with expandable editing; detail pages should prioritize the selected pattern.

17. **Problem list supports fewer tools than the backend.** `libraryInput()` supports practice status and topic filters, but the UI only exposes text search. Discuss adding difficulty, last-practiced and legacy/dates filters and a useful sort. Keep these scoped to the pattern; a separate global library is not necessary.

18. **Missing first-use guidance.** A new website workspace shows empty pattern rows and goal setup but has no clear extension/import/startup connection checklist. Add a short onboarding state with concrete install/import/recording steps and a way to dismiss it.

19. **Date labels are inconsistent.** `PatternProblems.jsx:10` and `PracticeInsights.jsx` use elapsed 24-hour periods for “Today”; history uses browser-local calendar dates; scoring uses Asia/Calcutta local days. Two Sum displayed “7 days ago,” “23/09/2026” in the category summary, and 22 Sept history entries. Some variation can reflect other category events, but all relative labels should use one explicit workspace calendar/timezone. Display time when same-day attempts would otherwise appear identical.

20. **Explain unknown evidence.** Prefer “Previous solve · date unavailable” to the isolated “Unknown” last-practiced label. Make inferred versus confirmed approach and imported versus self-recorded practice visible where decisions depend on them. Excluded Database problems are counted by the API but the web UI does not display the exclusion; explain this in import summaries so users can reconcile totals.

## Extension improvements

21. **Popup checks extension readiness, not API/database readiness.** `popup.js` pings the worker and current tab. Show separate extension, LeetCode, API and database status, linked to actionable recovery instructions. A worker-ready message does not mean saving is possible. Add a direct dashboard shortcut.

22. **Panel opening depends on network context.** `capture.js:15–20` awaits pending/context messages before displaying the UI; the context request has a 10-second timeout. Render immediately with loading feedback, then populate approaches. If context fails, show why only Needs classification is available and allow a retry before saving. The current fallback silently narrows the choices.

23. **Pending recordings are discoverable only on their original problem.** Storage keys are per URL (`service-worker.js:4`). Add a pending-recording count/list in Settings or popup and links to resume. Include save-success feedback after the prompt closes.

24. **Recording timestamp is panel-open time.** `capture.js:24` captures time before filling the form, and manual recording has no date field. Label manual logging as now or allow an explicit past practice date. For Accepted captures, prefer actual submission time when obtainable without introducing fragile scraping.

25. **Import progress and recovery can be clearer.** Setup has resumable ten-item checkpoints and preserves prior records, which is good. Add phases (scan, metadata, save, dates), added/already-present/excluded counts, last run time/account, and explicit waiting/retry explanation. Explain that recent dates are limited to up to 20 submissions. Keep the account and API requirements visible throughout.

26. **Recent-date initialization does not run after Skip.** `setup-retention.js:9,51–52` hides the action unless legacy setup is complete; skip only re-renders. Decide whether users who skip the full import should still be allowed to import recent practice alone. Current `initialize()` already accepts non-pending setup, but the UI does not offer it for skipped users.

27. **DOM observation is broad and should be profiled.** `capture.js:91` observes subtree, attributes and text throughout every matched LeetCode page. Scheduling is throttled to 150ms, but `schedule()` also reads context/result while a submission is active; adapter fallback scans spans/divs. Scope result observation and attribute filters where possible. Measure on real editor pages before calling this a performance defect.

28. **Compatibility still needs real Chrome checks.** Adapter title/topics/verdict selectors depend on LeetCode markup and English labels. Cover layouts, collapsed topics, contest pages, keyboard submit, SPA navigation, stale results, multiple tabs, page suspension and extension reload. Treat fixture success as useful evidence, not proof of current signed-in LeetCode support.

## Accessibility, reliability and maintenance

29. **Expose interaction state semantically.** Subpattern `ButtonBase` expanders lack `aria-expanded`/`aria-controls`; selected pattern links lack current/selected state; goal-profile buttons lack a pressed/selected semantic state. Placement Radio controls have no explicit accessible name. Use coherent radio groups or labelled alternatives, and avoid nested interactive radio/button structures.

30. **Manage recording focus.** The fixture showed focus staying on Submit after the recording region appeared. Add a keyboard-accessible announcement/focus strategy, Escape close and return focus. Since this is a nonmodal side region, avoid trapping all page focus unless it becomes a modal dialog. Tiny close and history/edit targets deserve touch-target testing.

31. **Make activity data available without hover.** The 8px activity cells use title/aria-label on generic, nonfocusable boxes. Provide a textual summary/table or navigable tooltip rather than requiring mouse hover to understand each day.

32. **Reduced motion is incomplete in JavaScript scrolling.** The theme disables CSS transitions/animations, but `Overview.jsx:99` explicitly requests smooth scrolling. Honor the user's reduced-motion preference in that call. Continue contrast/focus and screen-reader testing; no comprehensive accessibility certification was performed.

33. **Protect local data operationally.** Add export/backup and a verified restore workflow for attempts, notes, placements, imports and goals. Surface the bound LeetCode account and storage location in Settings. Existing soft deletion is valuable; an undo/recovery UI would make it useful to the user. No backups/restores or deletion were performed during this review.

34. **Local API hardening deserves a scoped review.** The server defaults to loopback, validates bodies and parameterizes SQL, but mutation routes have no origin/token guard. Before expanding beyond the current local personal setup, define trusted callers, readiness status and allowed hosts/origins, and review local-origin attacks. Absence of authentication alone is not a finding that an arbitrary remote webpage can currently read/write all data; exploitability was not tested.

35. **Prevent dashboard composition regressions with browser tests.** Tests strongly cover policies, HTTP contracts and persistence, but they missed featured-search contradictions and an unreachable editor. Add a small browser suite for search, detail/back navigation, history editing/pagination, goal display and mobile overflow, plus installed-extension tests where feasible. `npm run test:capture` starts a fixture server; it is not an automated browser test command.

36. **Improve loading and rendering robustness.** Refresh has no busy/last-updated feedback; goal form choices remain selectable while save is pending; React has no error boundary for malformed unexpected data. Add clear state transitions, preserve successful data and drafts, and prevent concurrent edits from visually contradicting an in-flight goal save.

37. **Optimize based on measurements.** Lazy-load detail/editor/insights, consider visibility-aware polling, and avoid repeatedly reclassifying/fetching the full problem catalog for every scoped list request (`repository.js:43,52,197`). Batch/index only where profiling justifies it. The measured local response was fast; there is no demonstrated current scalability incident.

38. **Clean up drift.** README describes mint/amber, no sidebar and historical editing despite the blue palette, desktop sidebars and unreachable editor. Align docs and `.21st` decisions with the chosen product. Review unused AttemptEditor/retentionFilters/attempt-form exports and old API/schema paths deliberately; do not delete persisted fields or migrations casually. Simplify dense one-line import/route code for maintainability after behavior is settled. Add extension icons and keep its version/release instructions coherent.

## Proposed discussion order

First agree on score continuity and whether goals should remain strict per-subpattern quotas. Then address search, history editing/pagination, missing metadata and account consistency. Next improve navigation, mobile layout, connection/offline states and pending recording recovery. Finally add focused browser regressions, backup/restore, accessibility work and measured performance improvements.

Keep the dark blue visual direction, independent practiced approaches, immutable uncertain-save retries, resumable imports and separation of Practice Strength from Goal Coverage. These are useful foundations; a new visual redesign is not required to solve the demonstrated problems.
