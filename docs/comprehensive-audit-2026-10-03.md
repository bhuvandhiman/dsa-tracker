# Recall robustness audit — 3 October 2026

## Result

Reviewed the API, database access and migrations, authentication and account lifecycle, classification/goal/retention policies, frontend request and form flows, extension capture/import/session handling, packaging and deployment configuration. Fixed reproducible integrity and concurrency failures and added regressions. The existing visual direction, classification policy, goal allocation and practice thresholds remain in place.

This is a code audit with local verification, not a guarantee that no defect remains or a production penetration/load test. No real LeetCode submission, hosted account deletion, Render deployment, or live workspace restore was performed. PostgreSQL integration cases use generated isolated schemas and remove those schemas after testing.

## Fixed findings

| Failure | Fix | Verification |
| --- | --- | --- |
| Retrying a saved capture could overwrite provider tags imported afterward. Concurrent retries could reach the mutation path before the account lock. | Lock the verified LeetCode account before checking the request ID. Identical saved retries return the stored recording before metadata writes; conflicts and removed recordings remain rejected. | Real PostgreSQL concurrent capture and import/retry regression. Existing legacy-hash and manual-classification replay tests pass. |
| An import between problem classification and paginated retrieval could produce an undefined placement and fail the page. Multi-query history and summaries could also mix snapshots. | Run library, history and summary reads in repeatable-read, read-only transactions on one connection. The dashboard already uses a consistent snapshot. | Import deliberately commits between library queries; the current page stays consistent and the next read sees the new problem. Existing dashboard snapshot regression passes. |
| A new hosted account already has a setup goal, causing a valid local backup's goal to conflict before any practice exists. | An explicit restore may replace the setup goal while the workspace has no problems. A populated workspace still rejects conflicting source records. | Restore into a different empty goal succeeds; populated goal conflicts fail; a later invalid record rolls back both the goal replacement and all inserts. |
| Duplicate backup identities could be silently dropped by `ON CONFLICT`. Bad JSON classification metadata and PostgreSQL's non-finite timestamps could leave the dashboard unusable. | Validate identities, duplicate keys, topic arrays, placements, practice units and finite timestamps before inserts; reject future practice evidence. Preserve schema, full-column, foreign-key, row-count and body-size checks. | Duplicate problems, string IDs, malformed topics, nonexistent units, infinite dates and future practice are rejected atomically. Existing timestamp and full backup round-trip tests pass. |
| Recomputed queue memory could make otherwise identical goal records conflict during restore. | Ignore derived `queue_snapshot` when comparing goal collisions; preserve the stored queue when the source goal matches. | A changed queue snapshot no longer blocks an otherwise identical restore. |
| A rollback failure could replace the original error and return a client with uncertain transaction state to the pool. | Share a transaction helper across repository operations, migrations, onboarding and exports. Discard clients if rollback fails; deletion cleanup also discards unusable clients. | Unit tests verify original-error preservation, commit/rollback behavior and client destruction; all migration, account-isolation and deletion integration tests pass. |
| Delayed frontend requests or forms could use the account that signed in later instead of the owner that opened them. | Bind private components to their rendered workspace owner. Verify the owner before dispatch and after responses, include the expected workspace header, reject stale tokens/results, and cancel superseded loads. | Regressions cover stale forms, changed token owners, owner changes during lookup, and late foreign responses. Browser logout removes the private view. |
| Logout, refresh callbacks and project configuration changes could race with session hydration. | Invalidate account generations immediately, discard obsolete callbacks, clear private UI on owner changes, and recreate the SDK connection when its project changes. Same-owner refreshes preserve the current form. | Request-generation regressions and browser login/logout/setup checks. |
| Extension refreshes were shared without an owner/version key; late storage writes could undo logout. | Bind refresh entries to owner and account revision; serialize session writes and logout removal; verify the owner again before using a token. | Concurrent refresh, account-switch-during-refresh, logout-during-refresh and logout-during-storage-write regressions. |
| The extension replaced a caller's cancellation signal. Authentication lookup could also outlive frontend request deadlines. | Combine caller and timeout signals. Bound frontend token lookup, SDK HTTP calls and session operations. Extension requests cancel while token refresh is pending and cannot dispatch a later data write. | Cancellation during fetch and token lookup/refresh is tested. Failed/uncertain recording payloads stay available for an identical retry. |
| A valid password-reset session could be blocked by private database unavailability. | Keep SDK session identity separate from verified workspace identity. Password recovery uses the SDK session; private pages still require successful server verification and setup. | Browser fixture reports a workspace 503 while the reset form remains enabled. No actual password was changed. |
| Malformed provider responses could throw or render invalid account values; rate limits looked like expired sessions. | Validate provider account/session shapes and token bounds. Return 503 for malformed provider accounts, preserve 429 rate limits, and expose only string email/name values. | Malformed/null/array responses, corrupt stored sessions, unverified users, network failures and rate limits are tested. |
| Corrupt queue memory could hold an unrealistic priority indefinitely. | Validate anchors, integer counters, target bounds and consistency between committed and last credited coverage. Rebuild invalid derived memory from source evidence. | Corrupt-memory regressions pass alongside all coverage/revision block and assistance-weight tests. |
| Taking a queued accepted event before persisting a draft could lose it if the panel closed or failed to open. Queue/message failures could reject without a response. | Transfer event evidence and remaining queue in one storage operation, protect an existing draft, bound queue/evidence size, reject malformed queue storage, and handle recorder message failures. | Restart, existing-draft protection, persisted event/time, malformed evidence and queue regressions. Browser offline retry preserves the exact request ID and choices. |
| A corrupt import checkpoint could skip batches or fail mid-run; a same-length metadata response could contain different problems. | Rebuild invalid checkpoints from a verified scan under the same run ID; replay idempotently. Validate snapshot uniqueness, offsets and each requested metadata URL before writes. | Corrupt offsets/snapshots replay from zero; mismatched metadata never reaches the write call. Existing resume and account-switch tests pass. |
| Configuration placeholders, unsafe external links, database-incompatible input text/dates and unexpected error logs had avoidable failure/privacy risks. | Detect literal password placeholder brackets with a safe configuration error, allow encoded real brackets, restrict problem links to valid HTTPS LeetCode paths, reject null characters/invalid Unicode/year zero at input validation, and redact unexpected errors in server logs. | Database URL, external URL, input-boundary and sensitive-error redaction regressions. |

## Checks and evidence

- `npm run check`: **246 tests**, ESLint and Vite production build pass.
- `npm run test:db`: **19 PostgreSQL integration tests** pass, including the new robustness suite.
- A volume integration case creates **1,000 distinct problems and 2,000 recordings**, verifies distinct counts and bounded progress in both preparation modes, and paginates the final page correctly. This is a representative data-volume check, not an internet concurrency benchmark.
- Goal tests cover both preparation modes and all three targets; difficulty quotas sum exactly to the selected total, overflow remains a displayed count, and block/correction/decay invariants pass.
- `npm audit --json`: **0 known vulnerabilities**, 289 dependencies assessed. No dependency upgrades were needed; vulnerability databases can change.
- Local and hosted extension packaging: ZIP CRC/integrity, unique safe paths, updated source/version and exact hosted permissions verified. The repository download is regenerated in local mode; Render's build generates the hosted configuration.
- Browser account fixture: login, logout, focus choice, extension acknowledgement, setup completion and recoverable dashboard failure checked.
- Browser outage fixture: valid SDK session keeps password recovery available when workspace loading fails, with private workspace access still blocked.
- Browser recorder fixture: fresh Accepted opens the real panel; offline save freezes choices; retry preserves the request ID and closes the panel on success. The inspected browser console showed no application warnings/errors.
- Applied SQL migration files were not rewritten. Existing migration checksum/backfill tests pass.

## Remaining operational and product limits

1. **Live Chrome and LeetCode:** fixtures exercise real scripts with simulated Chrome/provider messages. Reload version 0.10.1 in a signed-in Chrome profile and refresh LeetCode, then verify a real import, accepted recording, restart and multi-tab interaction. LeetCode DOM/GraphQL changes remain an external dependency.
2. **Hosted verification:** these edits have not been pushed or deployed. Real Supabase email delivery, production credentials/TLS configuration, Render restart behavior and account cleanup must be checked on the deployed service. Local mocks do not establish those outcomes.
3. **Operations before a wider launch:** provide the support/privacy contact and operational backup retention policy identified by the privacy page. Arrange provider/database backups and a restore drill; define hosting monitoring and abuse/traffic controls appropriate to expected usage. A free preview service is not a tested high-traffic deployment.
4. **Backup limits:** the browser currently accepts files up to 10 MB; the API caps restore bodies at 20 MB and 200,000 rows. Very large workspaces require an operational database backup/restore plan. Compatible snapshots add missing records; they do not overwrite newer conflicting practice.
5. **Policy interpretation:** retention is an estimate from practice evidence, not a measured memory score. Topic tags identify a conservative primary classification; they cannot prove the technique used in a person's solution. Explicit topic/Other choices remain the correction path. Daily evidence grouping currently uses Asia/Calcutta as documented; global per-user time zones are a separate policy change.

Commit and deploy the reviewed source changes using the existing Render build. Reload the unpacked extension, or download the newly generated hosted ZIP, then refresh open LeetCode tabs.
